Findings (read-only review of all requested artifacts):

P0 — legacy mapping is not honestly “every key mapped to a leaf.” `validation.legacyKeysAccountedForExactlyOnce=true` is technically true only because four reference keys are attached to composite service intents: `new-hire-setup`→`worker-master-setup`, `salary-certificate`→`employment-documents`, `pay-frequency-question`→`pay-access`, `final-pay-question`→`pay-release`. Exact recommended edits: create atomic leaves `new-hire-setup`, `salary-certificate`, `pay-frequency-question`, `final-pay-question`, remove those four `legacyReferenceKey(s)` from parent services, and point each reference row to the new leaf. Mark parent-level mapping only if product explicitly supports composite intents; otherwise the current mapping overstates runtime/leaf coverage. The other 56 reference keys map to leaves.

P0 — onboarding taxonomy is broad (48 leaves) but operationally under-specified at document/task granularity. `background-screening` has supporting-document collection but no named BGV document types, disclosure/authorization, report copy, dispute package, pre-adverse/adverse sequence. Exact edits under `background-screening`: add `request-bgv-disclosure-authorization`, `collect-bgv-document`, `deliver-bgv-report-copy`, `issue-bgv-pre-adverse-notice`, `record-bgv-dispute`, `issue-bgv-adverse-action-notice`, `record-bgv-vendor-result`; keep right-to-work separate. Add explicit `collect-tax-form`, `collect-direct-deposit`, `set-payroll-group`, `set-time-leave-profile`, `enroll-benefits`, `waive-benefits`, `resolve-carrier-enrollment-error` under payroll/tax/time/benefits setup (currently broad compound leaves). Add `revoke-prehire-access` and `recover-equipment-on-cancellation` as cancellation-specific leaves; current cancellation parent mixes pause/resume/cancel/reopen/transfer.

P0 — compound leaves remain despite the atomic rule. Programmatically, many names are deceptively atomic while descriptions/actions combine multiple outcomes. Highest-impact examples visible in taxonomy: `create-worker-record`/activation, `set-payroll-tax-time-benefits-eligibility`, `request-assign-ship-confirm-equipment`, `provision-badge-site-parking-desk-visitor-access`, `confirm-all-critical-readiness-gates`, `extend-confirm-fail-probation`, and `cancel-hire-revoke-access-recover-assets`-style leaves. Exact edit: split each verb chain into one leaf with one write/evidence record; retain an orchestration service intent above them. Especially split readiness into `check-day-one-readiness`, `record-day-one-attendance`, `record-day-one-no-show`, `activate-employment`; probation into `create-probation-plan`, `record-probation-check-in`, `extend-probation`, `confirm-probation`, `fail-probation`; cancellation into `cancel-hire`, `revoke-prehire-access`, `recover-assets`, `close-cancellation-case`.

P1 — missing lifecycle/service domains compared with the five drafts: no explicit standalone `HRIS/payroll/time/benefits enrollment` domain (currently one service); no standalone `facilities/workplace` domain (buried with equipment); no explicit onboarding `readiness/no-show` service; no explicit `manager/buddy` service; no explicit `probation` service (currently `probation-onboarding-change`); no explicit `hire cancellation` service; no explicit `BGV documents` service. Recommended service additions: `onboarding-data-enrollment`, `onboarding-access`, `onboarding-workplace`, `onboarding-learning`, `onboarding-manager-buddy`, `onboarding-readiness`, `onboarding-probation`, `onboarding-cancellation`, `background-screening-documents`; split ownership/system fields accordingly. Draft 1 explicitly treats these as separate accountable domains.

P1 — weak agent ownership. Taxonomy uses generic `HR operations specialist`, `Onboarding Operations specialist`, or `HR service desk` on leaves that drafts assign to distinct Payroll/Benefits Ops, IT IAM, Workplace/Facilities, L&D, HRBP/People Manager Ops, and People Compliance/Screening. Exact edits: set accountable agents to `People Compliance/Screening specialist` (BGV/right-to-work), `HR Operations/employee-data specialist` (worker master), `Payroll Operations specialist`, `Benefits Operations specialist`, `Time & Attendance/Leave specialist`, `IT IAM specialist`, `Workplace/Facilities Operations specialist`, `L&D/Onboarding Learning specialist`, `Onboarding Operations specialist` (communications/readiness), and `HRBP/People Manager Operations` (probation/cancellation). Add collaborator and approval fields per draft 1 mapping; do not use one generic owner for access + facilities + payroll.

P1 — duplicate/overlap boundaries: onboarding `background-verification` vs `identity-right-to-work` must remain separate (different legal basis/vendor/notices); `worker-master-setup` overlaps core-HR employee creation; `orientation-learning` overlaps `learning`/`learning-compliance`; `manager-buddy` overlaps generic communications; `first-week-activation` overlaps readiness/activation; `probation-onboarding-change` overlaps probation and change/cancellation; `device-facilities-setup` combines IT assets and physical facilities. Exact edits: add explicit `boundaryOf`/`handoffTo` metadata and split composite services; make recruiting own candidate/offer and Core HR own post-acceptance worker activation; make onboarding learning only mandatory pre-/early-tenure tasks.

P1 — missing atomic outcomes from drafts outside onboarding: core HR lacks explicit `SAR recognized/logged`, privacy deadline/clarification, search/redaction, and response delivery leaves; payroll lacks separate statutory filing/remittance/reconciliation and payment returned; time/absence lacks payable-time conversion/interface exception; ER lacks grievance meeting/decision/appeal and investigation evidence/finding as separate routable leaves. Add those leaves or document intentional exclusion. Drafts 2–5 explicitly call them out.

P1 — product-import shape is unsuitable. `journeys`, `serviceIntents`, and `subIntents` are nested/relational and require foreign-key resolution; `legacyReferenceKeys` is polymorphic (sometimes service, sometimes leaf), making import semantics ambiguous. `requesters`, `collaboratingAgents`, `systems`, `readActions`, `writeActions`, `completionEvidence`, `exactAliases`, and `sourceFamilies` are arrays/free text, not normalized import entities. `humanApproval`, `description`, `scope`, `targetMaturity`, and `currentCoverage` mix policy, prose, lifecycle state, and implementation status. `generatedOn`/`taxonomyVersion` are metadata, not row fields. Recommended edits: provide flat export with one row per leaf: `intentKey`, `journeyKey`, `serviceIntentKey`, `name`, `description`, `accountableAgentId`, `requesterIds`, `collaboratorIds`, `systemIds`, `flowClass`, `riskClass`, `approvalPolicyId`, `completionEvidenceTypeIds`, `aliasIds`, `legacyReferenceKey` (nullable, one-to-one), `jurisdictionOverlay`, `status`; normalize agents/systems/aliases/evidence/policies into lookup tables; enforce IDs/enums and avoid arrays/prose in import payload.

P2 — agent coverage artifact confirms a serious implementation gap: 58/60 reference intents are `unsupported`, 2 simulated, 0 integrated; therefore “mapped” must not be represented as executable coverage. Exact edit to coverage schema: separate `catalogued`, `mapped`, `simulated`, `integrated`, `verifiedProductionE2E`; set `mapped=true` only for canonical leaf mapping and retain `runtimeStatus=unsupported` for all 58.

P2 — candidate gaps in `intent-agent-coverage.json` are not represented as taxonomy leaves despite `candidateGapsCovered=true` (coverage artifact says candidate status, not canonical implementation). Promote only after review: standalone access request, candidate application status, candidate interview preparation, candidate recruiting-process FAQ, job requirements question, job recommendation request. Add `promotionStatus` rather than claiming coverage.

P2 — the taxonomy has 17 journeys/87 services/300 leaves and structural checks pass (unique keys, resolved references, allowed enums), but structural validity does not establish substantive coverage, atomicity, ownership, or product importability.
