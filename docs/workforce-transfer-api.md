# Workforce transfer API contract

All endpoints below are tenant-scoped by the authenticated Control Tower session. They are served from `/api` and reject a caller-supplied organization identifier. Dates are ISO-8601 strings. `version` fields are compare-and-set tokens: a `409` response means the client must reload before retrying.

## Programs and legal pathway

* `POST /onboarding/workforce-transfers/programs` creates a **planning-only** program. Required: `name`, `sourceLegalEntity`, `destinationLegalEntity`, `countries` (nonempty array), `proposedBasis` (`automatic-transfer`, `share-purchase`, `asset-purchase`, or `cross-border`), `legalDay1`, and `owners` containing nonempty `hrIntegration`, `legal`, `payroll`, and `it` user identifiers.
* `GET /onboarding/workforce-transfers/programs` returns tenant programs without population personal data.
* `GET /onboarding/workforce-transfers/programs/:programId` returns the program, population summaries, pathway decisions, and safe persisted cutover summaries. Each plan includes its readiness generation, sign-off role/decision/generation/current-authority state, and per-worker stream status with authority/current and evidence-present booleans. Private evidence, attestation references, terms, source payloads, and authority assignment IDs are omitted.
  Current HR Compliance authority can read the complete safe summary. Current Legal, Payroll, and IT Security specialists may read only programs/countries in their active jurisdiction scopes: Legal receives legal-safe summaries, while Payroll and IT receive worker identifiers and operational statuses only. Responses include `readCapabilities`; revoked or out-of-country specialist assignments cannot read a program.
* `POST /onboarding/workforce-transfers/programs/:programId/pathways` records a jurisdiction-specific Legal decision. Required: `expectedVersion`, `jurisdiction`, `reviewReference`, `decision` (`approved` or `rejected`), `offerRequirement` (`not-required`, `required`, or `legal-review-required`), and `bgvApplicability` (`not-required`, `required`, or `legal-review-required`). An approved decision records the current `legal-approve` authority assignment and revision. It does not create offers, BGV, or external effects. Every pathway field is material: changing any decision, requirement, review reference, authority generation, or decision date invalidates draft readiness and fences existing cutover plans.
* `POST /onboarding/workforce-transfers/programs/:programId/data-governance` records the jurisdiction-specific Legal-approved lawful sharing basis and retention schedule. Required: `expectedVersion`, `jurisdiction`, `lawfulBasisReference`, `retentionReference`, and `retentionUntil`. Both this approval and the country pathway must exist before a preview may retain any workforce row or an import may persist one. Any lawful-basis/retention reference, expiry, approval authority, approval date, or revision change invalidates draft readiness and requires a new cutover plan.

## Population mapping and import

* `POST /onboarding/workforce-transfers/programs/:programId/populations` creates a population (`country`, source/destination legal entity, and required approved `expectedHeadcount`). An import must contain exactly that number of valid stable-source rows; a cutover plan and Go decision recheck that exact count for every population.
* `POST /onboarding/workforce-transfers/populations/:populationId/imports/preview` validates rows without persisting worker data. Required: `mapping` and `rows`; rows must map stable `sourceWorkerId`, `workerName`, `workEmail`, `originalHireDate`, `continuousServiceDate`, `termsReference`, `compensationReference`, and `benefitsReference`. Optional permitted liability data is a **reference only**, never free text. Response contains row-level errors, duplicate source IDs, and mapping output.
* `POST /onboarding/workforce-transfers/populations/:populationId/imports` persists a preview. Required: `previewId`, `idempotencyKey`, and `expectedPopulationVersion`. It is retry-safe: the same key and identical preview returns its prior reconciliation; a changed payload/key pair returns `409`. Imports fail closed without current approved pathway and data-governance decisions for the population country.
* `GET /onboarding/workforce-transfers/populations/:populationId/reconciliation` returns count/status reconciliation only, never worker terms, compensation, benefit, liability, or evidence payloads.

## Restricted consultation and worker operations

* `POST /onboarding/workforce-transfers/programs/:programId/consultation-milestones` creates or supersedes a Legal-authorized milestone with `expectedVersion`, `jurisdiction`, `kind`, `dueAt`, `evidenceReference`, and `status`; include its stable `milestoneId` to update it. The reference is kept private and is not exposed through program summary endpoints. A milestone/action update invalidates draft cutover readiness generations.
* `POST /onboarding/workforce-transfers/workers/:workerId/objections` records a restricted objection/opt-out decision with `expectedWorkerVersion`, `outcome` (`pending`, `objected`, `withdrawn`, `resolved`), `receivedAt`, and `evidenceReference`. This never assumes a waiver or changes employment terms.
* `POST /onboarding/workforce-transfers/programs/:programId/integration-actions` creates or supersedes an owned `integration`, `induction`, `harmonisation`, or `contingency-parallel-run` action; include its stable `actionId` to update it. A `harmonisation` action requires a current Legal approval reference; the endpoint does not alter terms. A completed owned contingency/parallel-run action with evidence is required before Go.

## Cutover and evidence

* `POST /onboarding/workforce-transfers/programs/:programId/cutover-plans` creates an immutable plan version. Required `expectedVersion` and optional `contingencyReference`. It snapshots each jurisdiction’s complete pathway (reviewed basis, decision, offer/BGV requirements, review reference, authority, and decision date), data-governance approval (lawful basis/retention references and expiry, authority, approval date, revision), and currently imported workers. Go compares this complete snapshot to live records; any material change requires a new plan. No provider action is dispatched.
* `POST /onboarding/workforce-transfers/cutover-plans/:planId/workers/:workerId/reconciliation` records human evidence for `migration`, `payroll`, `benefits`, `access`, or `first-pay` using the current `expectedPlanVersion`, `status` (`pending`, `ready`, `complete`, `exception`, `unknown-effect-manual-repair`), and an `evidenceReference`. A completed `migration` additionally requires source/destination attestation references, destination original-hire/continuous-service dates, and destination terms/benefits references; dates and protected references must exactly match the retained source transfer record. Every reconciliation increments the plan version. `migration` requires HR Compliance authority; `payroll`, `benefits`, and `first-pay` require Payroll authority; `access` requires IT Security. An `unknown-effect-manual-repair` state cannot be overwritten without a separately recorded `repairReference`; that repair is preserved in an append-only repair record. `complete` means evidence was recorded, not that a remote operation was dispatched.
* `POST /onboarding/workforce-transfers/cutover-plans/:planId/signoffs` records an HR integration, Payroll, or IT sign-off using `expectedPlanVersion`. Legal-approved pathways, completed consultation, source reconciliation, and all three current sign-offs are required for `POST /onboarding/workforce-transfers/cutover-plans/:planId/go-no-go`. The decision is revision-fenced and records only a human go/no-go decision; it never claims pay/access continuity.
* `POST /onboarding/workforce-transfers/programs/:programId/kpi-definitions` first records an approved immutable metric revision with `metric`, `definitionReference`, and `denominatorReference`. The server snapshots the eligible cohort at approval: workers for worker metrics, consultation milestone IDs for consultation, and harmonisation action IDs for harmonisation. `POST /onboarding/workforce-transfers/programs/:programId/kpi-evidence` then records authorized dated source evidence with `metric`, `occurredAt`, `sourceAttestationReference`, `sourceRecordId`, `measurement`, and `evidenceReference`; `sourceRecordId` must be a member of that definition revision’s cohort (and is the worker ID for worker metrics). The server ignores asserted `value` and derives it from facts. First pay requires expected/actual amounts **and** `expectedCurrency`/`actualCurrency` plus `paidAt`; access requires granted/required dates; service-date requires `sourceFingerprint` plus source/destination original-hire and continuous-service dates, each verified against the immutable worker source record; consultation/harmonisation must bind a completed eligible milestone/action. `GET /onboarding/workforce-transfers/programs/:programId/kpis` selects latest evidence by cohort record, uses the revision-bound cohort size as the actual denominator, and reports unknown cohort members rather than treating a program as denominator 1.

All mutation endpoints return `{ version }` (and newly allocated IDs where applicable). Validation failures are `400`, restricted authority failures `403`, missing tenant records `404`, and stale/blocked decisions `409`.
