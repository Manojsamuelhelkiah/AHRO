# Transaction working context

The first adapter is onboarding. The `transaction-context/v1` response is a reusable, workflow-labelled transaction contract; it is **not** the execution-context manager, an agent memory, a chat thread, a workflow engine, or a source of decision authority. Onboarding's projection is assembled on each request from the tenant's current authoritative records under the reader's current effective human or registered-agent permissions. The SHA-256 source revision includes the accessible underlying rows, linked records, policy/edit gate and annotation versions, not merely the case update time. `asOf`, `summaryVersion`, per-source revision, provenance and explicit limitations accompany the deterministic summary. No projected case facts are stored in execution-history tables. Nothing in the summary may approve a package, validate a document, finish a workflow or replay an uncertain effect.

## Source inventory and ownership

The case row owns case state, the recorded original request, requested joining date, offer-acceptance status, readiness and workstreams. Approval and approval-history records own decisions; policy evidence, readiness-policy snapshots/attestations/ledger, system checks, events, day-one logistics, document validation state, and tenant-scoped operational requests own their respective details. A source's identifier, tab, row-derived revision and operational/scenario/human-annotation provenance identify where to review it. A navigation control only switches to an already-permitted case-detail tab. The projection says **not recorded** when an original request, owner, historical rationale or decision evidence is absent; it does not fill gaps with current policy or a generated narrative. A responsible role is not an assigned owner. Scenario-managed sources can be reviewed but cannot authorize operational completion.

All-class confidential field and notes access is required before querying approvals, events, validation rows, operational requests or handoff bodies. Even an authorized projection excludes communication bodies, raw files, object paths, document contents and provider payloads. The public Demo principal cannot see confidential narrative or annotations. Restricted collections are not queried merely to reveal their IDs, links or counts. Oversized collections return an explicit limitation and make further note editing unavailable; they are never silently treated as complete. Database/source failure is an error, not an empty or current summary. Per-case permissions, organization membership, agent ownership, case restrictions and the live field intersection apply at each read and again before response delivery.

## Handoff and consumers

Separately governed handoff revisions cover **open question**, **requested next work** and **handoff explanation**, at most 2,000 characters per revision. The server records authenticated author, time, monotonically increasing kind-specific revision, and the reviewed source revision. Empty text records a clear, without erasing previous revisions. A write requires current case and confidential edit privileges, non-retired operational state, approved all-class jurisdiction-specific collection/storage policies, unchanged full source revision and expected note-kind revision. It runs behind the sensitive-lifecycle organization fence and a row lock. A stale, redacted, concurrent or lifecycle-restricted write is rejected without overwriting a newer or hidden value. The protected audit receives an ID-only reference; note bodies do not enter immutable audit, metadata-only HRO execution history or raw-error logging. Existing legal/privacy holds, case-envelope retention and governed release/deletion govern all revisions together.

Supported consumers:

- The case-detail **Transaction context** tab: structured sections, source navigation/details, freshness, explicit limitations, scoped drafts, author/revision history, a manual refresh, and read-only display when edits are not allowed.
- Onboarding-agent preparation with a current initiating human and active owned agent, when its effective capability allows the read. The optional plan narrative retains authorized role, department, geography, worker/hire type, skills and rule-derived checklist adjustments. A changed profile or unavailable/denied context skips only the optional narrative, not the existing rule-based checklist or its human-approval checkpoint. Scheduled/system work without a user principal does **not** gain private context by default.
- The existing case-explanation evidence constructor: uses the same source references/revision and preserves allowlisted document/validation statuses, recorded blockers and task statuses, activity timestamps, system checks, human decision history and requirement/workstream statuses. Only fixed operational projections and handoff-presence markers go to external AI; opaque labels, blocker narratives, historical rationale, note bodies, messages and private file excerpts remain excluded. A missing or restricted rationale is never inferred. Existing exact-payload provider governance and human case-analysis restrictions still apply.
- The registered invocation tool `tool.context.read`: a **separate, read-only** capability requiring an active registered agent, its actual owner as initiator, live intersected case read and explicit context scope. The existing `tool.case.read` remains metadata-only.

The conversational Action Center can use the guarded API/read adapter once that separate workstream is ready; this release does not create chat persistence, triage, dispatch or a second action router. Other HRO workflows do not yet have source adapters or a case UI. Their authority and workflow-specific field rules need individual review before they join this common contract; in particular, absent offboarding closure requirements cannot be inferred from this adapter.

## Verification and publishing boundary

Forward migration `0116_transaction_handoff.sql` was reconciled against the development ledger and current schema; the OpenAPI client and validator were generated. Canonical workspace typechecking and the affected API/agent/explanation/lifecycle suites pass. Isolated API fixtures cover the human note → registered-agent read → changed domain state → human refresh journey, process restart, linked-source invalidation without a case timestamp, two-writer conflict, private redaction, owner/scope denial, public Demo/scenario isolation, prompt injection, holds and all-revision deletion. These fixtures deny external provider effects and assert no new communications or effect-journal writes; the post-agent domain change is a controlled fixture update, not a claim of autonomous operational execution.

The shared-context suite passes 12 tests, including sanitized document/blocker/timeline/decision-history coverage and optional plan preparation with authorized profile/checklist inputs, denied profile access and unavailable context. The explanation route/model suite passes 15 tests and the registered-agent invocation suite passes 7 tests.

The disposable HTTPS browser harness exercised note creation/reload, stale-edit conflict, source navigation, delayed-case response isolation and a denied refresh. Saved browser captures at 390, 768 and 1440 pixels show the served context. The focused browser run failed only its overbroad `textarea`-count assertion: another, still-authorized case form has a textarea even when the transaction context is hidden. The recorded DOM confirmed the context and its private note were absent; the assertion was narrowed to the handoff editor and was not rerun. The general `pnpm test:browser-regression` workflow and cost-explorer intent-routing smoke subsequently passed configured completion validation after the missing browser recorder was installed. The focused browser assertion remains an explicitly recorded verification limit, not a claimed green focused run.

This fork does not deploy or publish anything. The production database still needs the established forward-migration/startup safety sequence and the tenant's independently approved jurisdictional policies before real confidential annotations can be collected. Do not treat development reconciliation or browser fixtures as production readiness.
