The approved exception permits a controlled additive inventory of ten curated
fictional offline examples per existing Control Tower family in the explicitly
verified Demo workspace. Ten is a coverage target, not a cap: older examples
remain and list totals may exceed ten. Complementary scenarios must vary
supported request attributes and unresolved review needs, not just names.

Later authorization for [explicit operational preparation and activation](offline-operational-authorization.md)
supersedes this note's earlier permanent read-only and reporting-exclusion scope
for eligible fictional examples. Inventory creation stays developer-only;
activation is never automatic and does not restore retired run/reset tools.

**Why:** The product owner requested an additive sample inventory after retiring
synthetic execution controls, not a return of public creation, reset, simulation,
provider activity, authority, or genuine outcome measurement.

**How to apply:** Keep the exception developer-only and additive, with stable
new slot identities, concurrency-safe retries and permanent offline guards in
the initial insert. Do not replace evidence or populate client tenants. Ordinary
list visibility applies only to server-confirmed fictional offline identities;
volunteered historical identities retain separate restricted history access.
Read visibility uses exact case-scoped grants through the ordinary access
evaluator, not a tenant-wide role exception or a revived authority bootstrap.
Older coverage records may predate fictional provenance. Read display can
recognize only a canonical reserved coverage key paired with its exact fixed
fictional name and invalid-domain address; notes alone are not provenance.
Development population is not proof of published database population.

A merged task's provisioning report is not proof that the main development database contains the inventory.

**Why:** A merged report described 120 curated examples, while the running main workspace still contained only its 30 older cases and none of the curated slots.

**How to apply:** Verify current database inventory and authenticated list visibility rather than trusting copied counts. Apply only the approved, additive developer command to missing Demo slots; do not turn sample population into automatic startup or publishing behaviour.

**Fixed fictional disclosure:** Ordinary case-scoped profile/notes access may
show the fixed server-defined fictional request and review explanation, not
mutable stored narratives or private evidence. This is not sensitive-record
authority.

**Why:** Otherwise meaningful curated examples become unreadable to ordinary
Demo readers, while a blanket offline exemption could reveal private records.

**How to apply:** Project fixed definitions only for the verified fictional
inventory; continue enforcing case read grants, denials and narrative restrictions
on all other records.

**Reporting boundary:** Authorized offline and online cases belong in applicable
status counts and cohorts. Actual UAT and retained real/controller histories
remain isolated. Missing or simulated evidence is unknown, never business success;
only valid post-activation verified evidence may establish measured outcomes.

**Why:** The owner superseded offline-only reporting exclusions while preserving
evidence-based outcomes and genuine UAT isolation.

**Sample label boundary:** Sample case references are display labels, not verified
employee identities, evidence references, or authority. Simplifying names and
labels does not authorize changing stored provenance, dates, or execution fences.

**Why:** The product owner requested simpler sample identification while explicitly
preserving read-only/no-outreach/no-business-completion restrictions and unresolved
review needs.

**How to apply:** Hide redundant generated sample identifiers only in confirmed
fictional offline presentation. Preserve reference conflicts, missing-reference
warnings and pending verification; never substitute the case number for evidence.
